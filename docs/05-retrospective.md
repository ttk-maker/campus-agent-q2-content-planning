# 复盘与实际用时

开始记录：2026-11-06 16:05（Asia/Shanghai）。本地核心、真实模型与 Web 验收至 16:46，约 41 分钟；其后进行场景标签修复、最终提交与远端 CI 收尾，时间见 Git 提交与 Actions。包括规划、实现、模型等待、验证，不等于用户个人独立编码时长。

重点难点：区分估算与已消费、保留成功步骤、失败续跑不重复扣费、重规划不能抹掉已花费用、模拟耗时与真实截止时间共同约束。

真正暴露问题的是失败路径：模型能从 premium 切到 basic，却会在脚本工具参数上反复犯错。简单把错误回成“无效参数”不足以帮助小模型恢复；提供准确的参数契约比放宽守卫更可解释。首次故障用例达到了 16 步上限，后来反馈修复后 10 步成功；这两次都保留，避免只展示漂亮的成功日志。

状态设计的收获是把“本次 Agent 是否完整结束”与“某一步是否真实成功”分开。保存后模型失败不应抹去方案，生成失败也不能成为 succeeded；重复运行读取真实记录而不是重走固定流程。账本和产物必须共同事务提交，否则可能出现免费成功或扣费未产出。

工程取舍：原生循环足够承载这道题，无需为框架名称增加依赖；标准库 HTTP 与 SQLite 使离线可复现。相应代价是没有分布式调度、持久化网页 Trace 或生产级租户安全。未来优先做外部工具幂等/对账、更广泛真实模型评估、内容质量评测及流式进度，而不是先堆叠多 Agent。

未完成范围：没有真实内容服务、采购、发布和公网部署；没有大规模模型成功率统计；没有声称用户已经独立理解、修改或手动验收全部代码。范围符合题目允许的本地合成工具与运行方式。
